\section{Overview}

The DBMS Academic Portal is a role-based university management system that supports students, faculty members, administrators, training and placement workflows, timetable management, attendance, examinations, leave applications, feedback, resume management, internships, placements, and academic records.

The backend exposes REST APIs under the base path \code{/api}. The database is centered on \code{STUDENT}, \code{FACULTY}, \code{COURSE}, and \code{COURSE_OFFERING}, with supporting tables for registration, grades, attendance, notifications, and career workflows.

\section{Roles and Access Levels}

The portal supports the following user roles and role-specific capabilities.

\begin{itemize}[leftmargin=*]
  \item \textbf{ADMIN}: Manages users (students and faculty), room master data, term-end operations, and system switches such as enrollment/feedback activation.
  \item \textbf{STUDENT}: Uses enrollment, attendance, transcript/result viewing, exams, feedback, leave application, internship/placement application, and resume management modules.
  \item \textbf{FACULTY}: Base teaching role with dashboard, assigned courses, marks update, attendance update, TA application review, and notification features.
\end{itemize}

Faculty role designations (from \code{FACULTY.role}) are:

\begin{itemize}[leftmargin=*]
  \item \textbf{Faculty}: Standard faculty operations.
  \item \textbf{HOD}: Department-level course, offering, and prerequisite management.
  \item \textbf{PIC\_TT}: Timetable and exam schedule management.
  \item \textbf{PIC\_CDC}: Internship and placement opening/application management.
  \item \textbf{PIC\_EXAM}: Reserved designation present in schema for exam-role based expansion.
\end{itemize}

Additional functional flags used in API authorization:

\begin{itemize}[leftmargin=*]
  \item \textbf{Faculty Advisor flag} (derived in auth response as \code{isFacultyAdvisor}) enables advisor-specific leave review flows.
\end{itemize}

\section{Tech Stack}

\begin{itemize}[leftmargin=*]
  \item Backend runtime: Node.js with Express.js.
  \item Database: MySQL.
  \item DB driver: \code{mysql2}.
  \item Authentication and security: JWT (\code{jsonwebtoken}), password hashing with \code{bcryptjs}.
  \item File and form handling: \code{multer}.
  \item Data import for admin bulk upload: \code{xlsx}.
  \item Frontend: HTML, CSS, JavaScript (single-page style routing in browser).
  \item Deployment: Render.
\end{itemize}

\subsection{Hosting Details}

\begin{itemize}[leftmargin=*]
  \item Production backend/API is hosted on Render at: \url{https://dbms-project-i5b2.onrender.com}
  \item Production MySQL database is hosted on the cloud platform filess.io.
\end{itemize}

\section{Database Schema}

\subsection{Schema intent}

The schema separates master entities from transactional entities.

\begin{itemize}[leftmargin=*]
  \item Master entities: \code{STUDENT}, \code{FACULTY}, \code{COURSE}, \code{ROOM}, \code{INTERNSHIP_OPENING}, \code{PLACEMENT_OPENING}.
  \item Transactional entities: \code{ENROLLMENT}, \code{MARKS}, \code{ATTENDANCE}, \code{EXAM}, \code{FEEDBACK}, \code{LEAVE_APPLICATION}, \code{TA_ASSIGNMENT}, \code{INTERNSHIP}, \code{PLACEMENT}, \code{ACADEMIC_TRANSCRIPT}, \code{RESULT_HISTORY}.
  \item Bridge entities: \code{PREREQUISITE}, \code{INTERNSHIP_BRANCH}, \code{PLACEMENT_BRANCH}.
\end{itemize}

\section{Redundancy Addressed}

\begin{itemize}[leftmargin=*]
  \item Course and faculty descriptive fields are not duplicated in transactional tables.
  \item Branch eligibility is normalized using \code{INTERNSHIP_BRANCH} and \code{PLACEMENT_BRANCH}.
  \item Transcript and application snapshot fields are retained intentionally for historical consistency and auditability.
  \item Feature switches are centralized in \code{APP_SETTINGS} instead of adding new columns in multiple tables.
\end{itemize}

\section{Implementation Notes}

\begin{itemize}[leftmargin=*]
  \item Backend uses Express middleware for CORS, JSON body parsing, not-found handling, and centralized error handling.
  \item Authentication uses JWT and role checks for student, faculty, and admin APIs.
  \item Binary attachments are stored in the database for documents, resumes, and opening attachments.
  \item \code{APP_SETTINGS} is used for runtime toggles like enrollment and feedback windows.
  \item Frontend API abstraction is in \code{frontend/js/api.js} and calls backend endpoints under \code{/api}.
\end{itemize}

\section{Conclusion}

The DBMS Academic Portal schema uses explicit keys, foreign keys, and controlled denormalization to support transactional correctness and historical reporting. The API layer is role-oriented and maps clearly to student, faculty, and admin workflows.

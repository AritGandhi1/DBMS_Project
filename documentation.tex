\section{Overview}

The DBMS Academic Portal is a role-based university management system that supports students, faculty members, administrators, training and placement activities, timetable management, attendance, exams, leave applications, feedback, resumes, internships, placements, and academic records.

The backend exposes REST APIs under the base path \code{/api}. The database is designed around the main academic entities: \code{STUDENT}, \code{FACULTY}, \code{COURSE}, and \code{COURSE_OFFERING}, with supporting tables for registrations, marks, attendance, notifications, documents, and career services.

\section{Database Schema}

\subsection{Core design idea}

The schema separates master data from transactional data:

\begin{itemize}[leftmargin=*]
  \item Master entities: students, faculty, courses, rooms, and openings.
  \item Transactional entities: enrollment, marks, attendance, exams, leave applications, feedback, TA applications, internship applications, placement applications, and transcripts.
  \item Bridge tables for many-to-many relations: \code{PREREQUISITE}, \code{INTERNSHIP_BRANCH}, and \code{PLACEMENT_BRANCH}.
  \item Configuration table: \code{APP_SETTINGS} for feature flags such as feedback and enrollment availability.
\end{itemize}

\subsection{Relationship summary}

\begin{itemize}[leftmargin=*]
  \item One faculty member can advise many students, while each student has at most one advisor through \code{STUDENT.advisor_id}.
  \item One course can have many offerings across different terms through \code{COURSE_OFFERING}.
  \item One offering can have many enrollments, marks records, attendance records, exams, timetable rows, feedback entries, and TA applications.
  \item The \code{PREREQUISITE} table implements a many-to-many self-relationship on \code{COURSE}.
  \item \code{INTERNSHIP_BRANCH} and \code{PLACEMENT_BRANCH} implement many-to-many mappings between openings and eligible branches.
  \item \code{TIMETABLE} connects course offerings with physical rooms and time slots.
  \item \code{DOCUMENT} and \code{STUDENT_RESUME} hold uploaded binary data for student documents and resumes.
\end{itemize}

\section{Normalization}

The database is designed to follow the first three normal forms, and most core tables are also close to BCNF.

\subsection{First Normal Form}

The design satisfies 1NF because every attribute stores atomic values. Repeating groups are separated into their own tables:

\begin{itemize}[leftmargin=*]
  \item Branch eligibility for internships and placements is stored in \code{INTERNSHIP_BRANCH} and \code{PLACEMENT_BRANCH} instead of repeating branch values inside the opening tables.
  \item Course prerequisites are stored in \code{PREREQUISITE} instead of being packed into a single column.
  \item Marks, attendance, timetable, and enrollment are separated into distinct rows per student or offering.
\end{itemize}

\subsection{Second Normal Form}

The bridge tables use composite keys where required, and every non-key attribute depends on the full key:

\begin{itemize}[leftmargin=*]
  \item \code{MARKS(student_id, offering_id)} stores grade-related attributes that depend on the student-offering pair.
  \item \code{FEEDBACK(student_id, offering_id)} stores one feedback row per student per offering.
  \item \code{PREREQUISITE(course_id, prereq_course_id)} stores one prerequisite pair at a time.
  \item \code{RESULT_HISTORY(student_id, term_number)} stores exactly one result row per student per term.
\end{itemize}

\subsection{Third Normal Form}

The schema reduces transitive dependency by keeping independent facts in separate tables:

\begin{itemize}[leftmargin=*]
  \item Student profile data is stored only in \code{STUDENT} and not repeated in enrollment, attendance, or marks tables.
  \item Faculty profile data is stored only in \code{FACULTY} and referenced by foreign key.
  \item Course master data is stored only in \code{COURSE}; term-specific teaching data is stored in \code{COURSE_OFFERING}.
  \item Room details are stored only in \code{ROOM}; timetable rows reference the room instead of copying room attributes.
\end{itemize}

\subsection{BCNF-style design}

Most tables are close to Boyce-Codd Normal Form because determinants are candidate keys or foreign keys. For example:

\begin{itemize}[leftmargin=*]
  \item \code{COURSE.course_id} determines course name, credits, and branch.
  \item \code{FACULTY.faculty_id} determines faculty identity fields.
  \item \code{COURSE_OFFERING.offering_id} determines the teaching assignment for that term.
\end{itemize}

\subsection{Controlled denormalization}

A few tables intentionally keep redundant snapshot data for auditability and performance:

\begin{itemize}[leftmargin=*]
  \item \code{MARKS} stores assessment breakdown and grade for quick access.
  \item \code{ACADEMIC_TRANSCRIPT} stores historical grade records independent of the live marks table.
  \item \code{INTERNSHIP} and \code{PLACEMENT} store company, role, and package as application snapshots so that application history is preserved even if openings change later.
  \item \code{NOTIFICATION} stores sender and recipient routing data so messages remain readable after the source entity changes.
\end{itemize}

\section{Redundancy Addressed}

The schema removes avoidable duplication in the following ways:

\begin{itemize}[leftmargin=*]
  \item Course and faculty details are not copied into enrollment rows.
  \item Course-offering details are not copied into transcript or feedback data.
  \item Branch eligibility is normalized into bridge tables rather than repeated text lists.
  \item Derived totals are generated where possible, for example the \code{total} column in \code{MARKS} and \code{ACADEMIC_TRANSCRIPT}.
  \item The key-value table \code{APP_SETTINGS} prevents extra columns for every future system flag.
\end{itemize}

\section{Implementation Notes}

\begin{itemize}[leftmargin=*]
  \item The backend is an Express application with CORS, JSON parsing, and role-based route protection.
  \item Authentication is handled with JWT tokens and middleware checks.
  \item Binary uploads are supported for documents, resumes, internship attachments, and placement attachments.
  \item Feature toggles in \code{APP_SETTINGS} allow the admin to enable or disable enrollment and feedback without changing code.
  \item The frontend API layer in \code{frontend1/js/api.js} wraps all REST calls and is aligned with the backend route structure.
\end{itemize}

\section{Conclusion}

The schema is normalized, modular, and suitable for a full academic portal. It separates master data from transactional records, reduces redundancy, supports historical tracking, and exposes a clear REST API surface for student, faculty, and admin workflows.
